# Identity Adversarial Suite Specification

## 1. Purpose and Scope
The `IdentityAdversarialSuite` (`org.upspa.assetlinks.adversarial`) is an exhaustive, data-driven security test harness designed to stress-test the UpSPA Digital Asset Links verification engine against adversarial edge cases, including:
- Domain boundary confusion (subdomains, siblings, ports, lookalikes).
- Package name spoofing and lookalikes.
- Certificate fingerprint tampering, truncation, and collisions.
- Conflicting and ambiguous evidence representation families.
- Multi-signer security bypass attempts.
- APK key rotation lineage edge cases.
- Cross-origin statement replay and injection.

---

## 2. Table-Driven Architecture

### Data Case Structure
Every adversarial scenario is defined as an immutable `IdentityCase` record in `IdentityCaseCatalog`:
```kotlin
data class IdentityCase(
    val id: String,
    val category: Category,
    val description: String,
    val build: () -> CaseInput,
    val expected: Expected,
    val bothEntryPoints: Boolean = true
)
```

- **`id`:** Distinct uppercase identifier (e.g. `EXACT_MATCH_SINGLE_SIGNER`). Used in Gradle reports and parameterized test naming.
- **`category`:** The security classification of the adversarial attack.
- **`build`:** Lazy factory generating `CaseInput(requestedOrigin, appSigningInfo, evidence)`.
- **`expected`:** Discriminated union of expected outcomes:
  - `Expected.Verified(assertFields)`
  - `Expected.Rejected(expectedClass, assertFields)`
  - `Expected.ConstructionRejected(expectedException)`
- **`bothEntryPoints`:** When `true`, executes against both `PureAssetLinkVerifier` (in-memory evidence) and `UpSpaAssetLinkVerifier` (via `FakeAssetLinkFetcher`), asserting identical outcome types and key properties. When `false`, documents the single entry point exercised (e.g. origin mismatch on evidence source origin).

## 3. Categories and Coverage

The suite defines 9 security categories with a minimum of 3 cases per category (total 50 cases):

| Category | Description | Primary Attack Vectors Tested |
| :--- | :--- | :--- |
| `EXACT_MATCH` | Baseline authorized relationships | Single signers, case normalization of hosts, non-default ports, default port 443 omission equivalence. |
| `PACKAGE_MISMATCH` | Package name confusion & lookalikes | Different package names, case alterations (`Com.Example.App`), prefix lookalikes (`evil.com.example.app`), suffix lookalikes (`com.example.app.evil`), non-Android namespaces (`web`), malformed identifiers. |
| `CERTIFICATE_MISMATCH` | Certificate fingerprint variations | Digest replacement, single-byte modifications, prefix-matching digests, statements authorizing certificates for other packages. |
| `ORIGIN_BOUNDARY` | Domain and URI boundary attacks | Subdomains, parent domains, sibling domains, lookalike hyphenated domains (`evil-example.com`), dot-suffix lookalikes (`example.com.evil.com`), distinct ports, insecure HTTP, trailing dots, path/userinfo injection, non-ASCII hosts. |
| `MALFORMED_CERTIFICATE` | Corrupt or invalid certificate data | Corrupt DER byte arrays, valid X.509 certs with trailing garbage, malformed hex fingerprints in app signing info or statements, mixed valid/invalid fingerprints, empty strings. |
| `CONFLICTING_EVIDENCE` | Multi-family ambiguity | Multiple active representation families in `AppSigningInfo` (typed + raw-string, typed + raw-bytes), no active family, signers omitted from key rotation history. |
| `MULTIPLE_SIGNERS` | Multiple APK signers safety | Multiple concurrent signers where one is authorized, multiple concurrent signers where both are authorized, multi-signers combined with key rotation lineage. |
| `ROTATION` | APK key rotation lineage | Lineage matching latest key, lineage matching historical key, lineage matching neither, signer not positioned at the end of lineage, deep history (> 2 keys). |
| `REQUESTED_ENROLLED_BINDING` | Origin binding & statement replay | Source origin matching requested origin, replaying statement from `example.com` to `evil-example.com`, subdomains, parents, alternate ports, alternate schemes, missing permission relation. |

## 4. Meta-Tests

The suite contains two mandatory meta-tests that validate the integrity of the test harness itself:

1. **Category & ID Completeness (`meta-test case IDs unique and categories have at least 3 cases`):**
   - Asserts that all case IDs are strictly unique.
   - Asserts total case count is $\ge 45$.
   - Asserts every category has at least 3 cases.

2. **Rejection Coverage & Allow-List Enforcement (`meta-test reachable rejection coverage and allow-list assert against reality`):**
   - Inspects `VerificationResult.Rejected` sealed subclasses via Kotlin reflection.
   - Asserts that every reachable rejection subtype is generated by at least one adversarial case.
   - Requires an explicitly justified allow-list for unreachable or fetch-layer-only rejections:
     - `RedirectAttempted`: Fetcher-layer only (HTTP 301/302).
     - `FetchFailed`: Fetcher-layer only (HTTP 4xx/5xx).
     - `NetworkError`: Fetcher-layer only (Socket/TLS failure).
     - `InvalidContentType`: Fetcher-layer only (non-JSON header).
     - `NoSigningCertificatesFound`: Structurally unreachable behind `AppSigningInfo` non-empty invariants.
     - `InvalidJsonFormat`: Raw-JSON entry point only (`verifyRawJson`).
     - `InvalidOrigin`: Raw-string URL entry point only (`verify(rawOriginUrl)`).
     - `RequestedPackageMismatch`: Produced only by the `RequestedIdentity` overload of `AssetLinkVerifier.verify`, which this case table does not drive; covered by `ReviewRound5TypedOutcomeTest`.
   - Dynamically asserts that no allow-listed class is produced by a case (detects stale allow-list entries).

---

## 5. Relationship to Existing Tests
- `AdversarialNegativeControlTest.kt`: Focuses on negative unit controls for specific parser edge cases and fetch errors.
- `IdentityAdversarialSuite.kt`: Systematically validates cross-layer identity binding, origin boundaries, and dual-verifier parity across comprehensive attack categories. It complements and does not replace existing tests.

---

## 6. Observed verifier behaviors to confirm with the reviewer
- A lineage whose declared current signer is not the newest entry still verifies (`ROTATION_CURRENT_NOT_LAST_IN_HISTORY`).
- An assetlinks statement listing only an older lineage key authorizes the rotated app (`ROTATION_LINEAGE_MATCHES_OLD`).

---

## 7. Known Limitations
1. **Injected Evidence:** Tests execute in pure memory without live HTTP socket connections.
2. **PSL / IDNA Handling:** `Origin` accepts only ASCII host characters, so non-ASCII (Unicode) hosts and trailing-dot hosts are rejected at origin construction, while punycode (`xn--...`) hosts are plain ASCII and are accepted as opaque literal strings without IDNA/UTS #46 validation and without any Public Suffix List logic. Full IDNA and PSL handling is deferred as a future roadmap item (`ID-01..04`).
3. **Format vs Deployment:** Verifying a statement in-memory proves mathematical and structural validity, not that an origin has deployed the statement on the public Internet.
